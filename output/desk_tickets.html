Why the order mattered

Running 101 → 102 → 103 was not arbitrary. Paying invoice 501 first cleared the only apparel vendor the shop has, so ticket 103 could at least price a real restock. Paying rent second protected a fixed obligation due in two days. Had 103 run before 102, the $264.00 restock would have been affordable out of $2,560.00 — and the shop would then have been $104.00 short of its rent. The agents never saw that trade-off; the run order made it for them.

Expected vs. Actual what the plan got right, and what it missed

The scoreboard

Six predictions per ticket — who the Boss calls first, how many hand-offs, how many approvals, how many drafts, the status path and the closing balance. All eighteen held. Every divergence was in how the team got there, not where it ended up.

  • ≠101 — one planned call never happened. Inventory was expected to use list_vendors. It didn’t need to: get_vendor_invoice already returned the vendor, the 5-day lead time and the blocked flag. Accounting called list_vendors later instead. The plan over-specified the route, not the answer.
  • ≠103 — the guardrail never fired. The plan said “request_purchase_order should refuse it, since checking can’t cover $264.00.” Accounting read the balance, did the subtraction and declined to call the tool at all. The outcome matched; the mechanism didn’t. That guardrail has still never been exercised on this board — across the whole run, zero tool calls were refused. It is tested nowhere except in the server code.
  • ≠103 — the warning landed one step early. The plan watched for “a discount quoted on all 20 hoodies as if they were in stock.” That is exactly what Accounting produced. The Boss and the draft then narrowed it to the 8 on hand. The risk was real and the plan spotted it; it just showed up in the quote rather than in the promise.
  • ×101 — the plan called it and I scored it wrong. The “Watch for” list warned about “a draft that… mentions the shop’s unpaid bill.” Draft 1 does exactly that, and the Actual section on the 101 tab originally recorded it as clean. The plan was sharper than the review of it. That tab now says so.
  • ✓102 — predicted to the hop. Including the three-deep Facilities → Accounting chain, the absence of a landlord draft, and the exact $2,560.00 → $160.00 closing balance. The ticket with the simplest shape was the one the plan nailed completely.

What this says about planning agent runs. Predicting outcomes turned out to be easy — the shop’s data only permits one sensible answer per ticket. Predicting paths was unreliable: tool choice, who calls what, and whether a guardrail or the agent’s own arithmetic stops a bad action all moved around. The valuable half of the plan was the “Watch for” lists, which caught a real failure the summary missed.

Would one agent with the same tools have done better? mostly yes

Where the team shape cost more than it bought

15 of the run’s 36 tool calls were repeats — one agent re-reading a row a teammate on the same ticket had already read. Every delegated agent starts with a fresh context and a task string, so it re-fetches the ticket and re-checks the numbers it was just told. That is 42% of the tool traffic buying nothing.

  • ≠Ticket 102 is the clearest case. Three agents, two hand-offs, 9 model turns, 22,411 tokens and 26.4 seconds — to produce one request_rent_payment call. The actual work is three lookups in a fixed order: does the notice match lease 1, can checking cover it, file the request. One agent holding get_lease, get_cash_balance and request_rent_payment does that in two turns. list_approval_requests was called three separate times by three different agents on that single ticket, and returned the same empty list each time.
  • ≠Ticket 103 re-read the same shelf three times. check_stock_and_price for CC-HOOD-NAVY size M was called by Inventory, then Accounting, then Customer Service. quote_bulk_price ran three times, list_vendors and get_cash_balance twice each. Seven of its fourteen calls were duplicates.
  • ≠Ticket 101’s fact-finding is a straight line. Check the shelf → check the invoice → file the payment → write the draft. No step needed a second opinion, and no branch depended on one. get_ticket was fetched three times by three agents.
  • ≠The whole shop fits in one prompt. Campus Customs is 10 inventory rows, 4 prices, 3 vendors, 1 invoice, 1 lease, 1 balance and 3 tickets. There is no context-window pressure here that splitting the work relieves. A single agent could hold the entire state of the business and still have room.

Where the team shape genuinely earned its keep

  • ✓Authority, not intelligence. Only Accounting can file a payment request. Only Customer Service can save a draft. Facilities can verify a $2,400.00 rent notice but cannot act on it, and no agent at all can move cash — pay_approved_request is not in any toolset. That is access control enforced by the toolset itself, and it survives an agent reasoning badly. One agent holding all 19 tools would need the same restriction re-imposed as a rule it could talk itself out of.
  • ✓An audit trail that answers “who decided this”. Every one of the 108 entries this run appended carries the agent and the delegation chain. “Why did the shop pay $840.00?” resolves to Inventory found the block → Accounting filed it → Manuel Sosa approved it. A single-agent log would show the same tool calls with no answerable question of responsibility.
  • ?The one “win” I don’t fully credit. On 103, Inventory recommended a $264.00 purchase order and Accounting refused it on cash. That reads like two specialists checking each other — but a single agent holding get_cash_balance would have seen $160.00 against $264.00 just as plainly. The disagreement was manufactured by splitting the tools, not by having two minds on the problem.

Verdict for a shop this size. One agent with all 19 tools, plus the hard rule that payment tools require a human, would have produced the same three outcomes faster, for roughly a third of the tokens. The five-agent shape bought separation of duties and a legible audit trail — both worth having when real money moves — and bought nothing in the quality of the answers. It starts to pay for itself when there are more tickets than one context can hold, or when the jobs need genuinely different authority, not merely different labels.

Three it can’t and what each would take

  1. Actually taking the Yale AI Club’s $417.60

    The team priced 8 navy hoodies at $52.20 each and drafted the offer. If the club says yes tomorrow, nothing in this system can book it. No tool decrements inventory.qty, nothing credits cash_accounts, there is no sales table, and payments records money leaving only. The eight hoodies stay on the shelf in the database forever and the $417.60 never arrives.

    This is the deepest hole in the design, and it is why $160.00 is a floor rather than a low point: the shop can spend and cannot earn. Every forward-looking answer the team gave — the $264.00 restock, the $2,240.00 rent gap — assumes no revenue, because there is no way to record any.

    What it would take

    A record_sale(ticket_id, sku, size, qty, unit_price, taken_by) tool that decrements inventory and credits checking in one transaction, refusing to sell stock that isn’t there or below pricing.unit_cost. A sales table mirroring payments, so money in is as auditable as money out. A Sales agent (or the authority added to Accounting) — and the same two-step gate as payments, because a wrong price charged to a customer is as costly as a wrong payment.

  2. Replying to Tauhid — and handling what he writes back

    Draft 1 has sat on the board since the run and there is no way to send it: no email tool, no phone, no outbox. There is also no way in. If Tauhid replies “fine, I’ll take a medium instead”, nothing turns that into a row in tickets — someone types it by hand or it is lost.

    And this run proved the draft itself isn’t safe to send. Draft 1 tells a customer that “the vendor’s invoice block must be cleared before an order can be placed” — an unpaid invoice disclosed to the person waiting on the order, which Customer Service’s own prompt forbids. save_message_draft stored it without reading it. A send button added today would ship that sentence.

    What it would take

    An outbound send_draft(draft_id, approved_by) gated exactly like pay_approved_request: human-only, never in an agent’s toolset, refusing an approver named after an agent. An inbound path that writes replies into tickets with a thread id, so a conversation is a ticket history rather than a one-shot. A content check before the human sees it — either a reviewer agent whose only job is to read drafts against the forbidden list, or a rule inside save_message_draft that refuses text mentioning invoices, balances, margins or unit costs. Prompts alone demonstrably did not hold.

  3. Receiving the reprint — and the fact that Sep 5 never arrives

    Say the $8.00 tee order goes in. Bulldog Print Co delivers on 2026-09-05. Nothing in this system records that: approval_requests.expected_arrival stores a date, but no tool increments inventory.qty, closes the purchase order, or reconciles 1 unit ordered against however many turn up. The shop would pay for a tee and still show 0 on hand in Aisle B.

    Worse, the shop’s clock is frozen. desk.date_today is pinned at 2026-08-31, and every overdue and due-soon check in the MCP server reads from it. Sep 5 never comes, October rent never falls due, and nothing scheduled for the future can ever be acted on. The team can only ever reason about one single day.

    What it would take

    A receive_shipment(request_id, sku, size, qty_received, received_by) tool that writes to inventory, marks the order delivered and flags a short or over delivery against what was approved. A Receiving agent to own damaged and partial deliveries, which is a judgement call Inventory’s read-only tools cannot make. A clock — an advance_day tool, or desk.date_today tracking the real date — plus something that re-opens a ticket when a promised date arrives. Without that last piece the other two tools would have nothing to trigger them.

If I were to carry on

  • Give the Boss a reason to call list_tickets. It has the tool and never used it. Working tickets in isolation is what let 102’s rent consume the cash 103 needed; only the run order saved the shop.
  • Validate draft text in code, not in the prompt. One sentence slipped through on the very first live run that produced a customer message.
  • Exercise the refusal paths. Not one of them fired across three tickets. Everything the shop’s rules forbid is, so far, untested by anything but the code that implements it.
  • Close the loop or stop quoting. Until there is a way to take money and receive goods, every ticket ends at a draft nobody can send, and the balance can only go down.
